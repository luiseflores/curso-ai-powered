man · repositorio

man repositorio

¿Qué es un repositorio?

  • Carpeta de proyecto que Git está versionando. "Repo" es la forma corta.
  • .git/ es la base de datos real del repo (historial completo) — nunca se edita a mano, se crea sola con clone/init. Borrarla borra el historial, no tus archivos.
  • .gitignore es distinto: un archivo de texto normal que le dice a Git qué nunca versionar.
  • Sin .gitignore, un git add . subiría credenciales o carpetas enteras de dependencias.
curso-ai-powered/
├── .git/        # historial completo (oculta, no se edita a mano)
├── .gitignore   # qué NUNCA versionar
├── README.md
└── CLAUDE.md

# .gitignore de este curso:
.env
node_modules/
carpeta versionada por git .gitignore nunca credenciales
concepto06 / 20

Un repositorio es una carpeta de proyecto que Git está versionando — tiene adentro una carpeta oculta .git/ con todo el historial. "Repo" es la forma corta de decirlo. .git/ es la base de datos real del repo: nunca se edita a mano, se crea sola con clone o init, y si la borran pierden el historial (no los archivos). Distinto es .gitignore: un archivo de texto normal que le dice a Git qué NUNCA versionar — en este curso, .env (credenciales, lo vemos en detalle la próxima clase) y node_modules/. Sin .gitignore, un git add . subiría eso al repositorio.

man · git-daily

git --daily-commands

Comandos git de trabajo diario

  • git fetch trae qué cambió en el servidor, sin tocar tus archivos todavía.
  • git status muestra el estado actual de tu copia local; git pull trae y aplica los cambios.
  • git add . marca lo que cambiaste; git commit -m lo guarda en el historial.
  • git push sube el commit — hoy no vemos branch, eso viene después.
$ git fetch   # trae qué cambió, sin tocar tus archivos todavía
$ git status  # muestra el estado actual
$ git pull    # trae los cambios y los aplica a tu copia local
$ git add .   # marca los cambios para el próximo commit
$ git commit -m "mensaje"  # guarda ese punto en el historial
$ git push    # sube tus cambios (ya commiteados) al servidor
fetch status pull add commit push hoy no: branch
concepto07 / 20

Hoy vemos seis comandos, los que van a usar todos los días: git fetch trae qué cambió sin tocar nada todavía, git status muestra el estado actual, git pull trae y aplica los cambios. git add . marca lo que cambiaron, git commit -m lo guarda en el historial con un mensaje, git push sube ese commit al servidor. No vemos branch hoy — eso viene cuando trabajen con ramas.

prompt · anatomy

prompt --anatomy

Las 4 piezas de un buen prompt

// tarea
Qué querés que haga, con un verbo concreto.
// contexto
Qué necesita saber el asistente para no inventar.
// restricciones
Qué NO tiene que hacer, o los límites del resultado.
// formato
Cómo tiene que verse el output (lista, tabla, código, etc.).
siempre las mismas 4 aplican en cualquier área
concepto13 / 20

Todo buen prompt tiene las mismas 4 piezas, sin importar el tema: tarea (qué querés que haga), contexto (qué necesita saber para no inventar), restricciones (qué NO tiene que hacer) y formato (cómo tiene que verse el resultado). Dominan esto y lo aplican en cualquier área, sepan o no del tema.

prompt · tips

prompt --tips

Consejos para aplicar ingeniería de prompt

  • Definí el resultado observable antes de escribir el prompt. Si no podés describir un output perfecto, no lo vas a poder pedir ni evaluar.
  • Las 4 piezas siempre son las mismas: tarea, contexto, restricciones, formato.
  • El "qué NO hacer" pesa tanto como el "qué hacer". Frenar errores típicos evita que el modelo invente.
  • Usá al modelo para investigar antes de pedirle que ejecute. No necesitás dominar el dominio, necesitás saber qué preguntar.
  • Iterá y guardá lo que funciona. Un prompt se prueba, se ajusta, y se convierte en plantilla reusable.
observable 4 piezas qué NO hacer iterar y guardar
concepto15 / 20

Cinco consejos para llevarse hoy. Uno: definan el resultado observable antes de escribir el prompt — si no pueden describir cómo se ve un output perfecto, no lo van a poder pedir ni evaluar. Dos: las 4 piezas siempre son las mismas, tarea, contexto, restricciones, formato. Tres: el "qué NO hacer" pesa tanto como el "qué hacer" — frenar errores típicos evita que el modelo invente. Cuatro: usen al modelo para investigar antes de pedirle que ejecute — no necesitan dominar el dominio, necesitan saber preguntar qué les falta saber. Cinco: iteren y guarden lo que funciona — un prompt se prueba, se ajusta, y se convierte en plantilla reusable.

¿Qué es una skill?

  • Paquete de instrucciones que le enseña al asistente a hacer una tarea específica.
  • La hace de forma reproducible — en vez de explicarle todo de cero cada vez.
  • El asistente la lee cuando la necesita, no en cada mensaje.
paquete de instrucciones reproducible
concepto16 / 20

Ese último consejo, guardar lo que funciona como plantilla reusable, es exactamente lo que resuelve una skill. Una skill es un paquete de instrucciones que le enseña al asistente una tarea específica de forma reproducible, en vez de explicarle todo de cero cada vez que la necesitan.

¿En qué se diferencia de un prompt? Un prompt es de un solo uso: lo escriben, lo mandan, se pierde al cerrar la conversación. Una skill toma ese mismo trabajo de ingeniería de prompt ya afinado y lo empaqueta para reusar: se guarda en disco, persiste entre conversaciones, y el asistente decide solo cuándo aplicarla.

skill · best-practices

skill --best-practices

Cómo se arma una buena skill

  • Paquete reutilizable, no instrucción de una sola vez. Carpeta con SKILL.md, persiste entre conversaciones.
  • La descripción es la parte más crítica. Es lo único que el asistente mira para decidir si aplica; si es débil, nunca se activa.
  • Se carga en capas. Nombre y descripción primero, cuerpo completo después, recursos extra solo si hacen falta.
  • Instrucciones claras, en imperativo, con ejemplos. Un buen input → output vale más que párrafos de reglas.
  • Se crea igual que un buen prompt: se prueba, se evalúa, se ajusta — pero queda como activo permanente.
reutilizable descripción crítica carga en capas
concepto19 / 20

Cinco cosas que hacen que una skill funcione. Uno: es un paquete reutilizable, no una instrucción de una sola vez — se guarda como carpeta con un SKILL.md y persiste entre conversaciones. Dos: la descripción es la parte más crítica — es lo único que el asistente mira para decidir si aplica; si es débil, la skill nunca se activa. Tres: se carga en capas — nombre y descripción primero, cuerpo completo después, recursos extra solo si hacen falta. Cuatro: instrucciones claras, en modo imperativo, con ejemplos — un buen ejemplo de input-output vale más que párrafos de reglas. Cinco: se crea igual que un buen prompt, se prueba y se ajusta — la diferencia es que una vez afinada queda guardada como activo permanente.
